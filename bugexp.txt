## 🐛 Root Cause Analysis — 4 Bugs Found

### Bug 1 (PRIMARY): Plan is generated but the AI ignores it during execution
**File:** `ai/decision_engine.py` → `_get_ai_proposal()`

The plan was being stored in `state.current_plan`, but when the autonomy loop resumed after approval and called `_get_ai_proposal()`, there was a **comment literally admitting the bug**: *"The extra context (like active_plan) is not part of the formal schema passed to adapters — this is a current limitation."* The LLM received no information about the plan, so it free-wheeled instead of executing step 1.

**Fix:** `_get_ai_proposal()` now finds the next incomplete plan step and passes it as `next_step_hint` to `get_recommendation()`. All three adapters (Gemini, Groq, Anthropic) now inject a hard instruction into the prompt: *"You MUST execute this exact next step."*

---

### Bug 2 (CRITICAL): Loop stops immediately with "heartbeat stale" before any action runs
**File:** `ai/context_manager.py` → `validate_readiness()`

Every autonomy cycle calls `_check_stop_conditions()`, which calls `validate_readiness()`, which checks if the executor's last heartbeat was within 30 seconds. In simulation mode, the executor never posts heartbeats, so this check always fails and the loop terminates on the very **first cycle** after plan approval — before a single action is queued.

**Fix:** The heartbeat check is now skipped for simulator/loopback executors (IP `127.0.0.1` or name containing `sim`/`local`). Real VM executors still get the full liveness check.

---

### Bug 3 (MEDIUM): `approve_plan` reads `llm_provider` after mutating `state_data`, and context not always reactivated
**File:** `dashboard/views.py` → `approve_plan()`

Two issues: (a) `llm_provider` was read from `state.state_data` *after* setting `plan_approved=True` on the same in-memory dict object — harmless now but fragile. (b) The context reactivation only fired `if status == 'STOPPED'`, but `request_initial_plan()` leaves the context at `READY`, so the reactivation block was silently skipped on a fresh attack.

**Fix:** `llm_provider` is read first, and the context reactivation now fires for both `STOPPED` and `READY` states.

---

### Bug 4 (MINOR): `_parse_plan` uses `SimpleNamespace` instead of `PlanStep` dataclass (Gemini & Anthropic)
**Files:** `ai/llm/gemini.py`, `ai/llm/anthropic.py` → `_parse_plan()`

Both adapters created `SimpleNamespace` objects for plan steps instead of proper `PlanStep` dataclasses. This works incidentally but produces inconsistent types vs the Groq adapter and can cause subtle attribute-access failures when the LLM returns unexpected keys.

**Fix:** Both adapters now create `PlanStep` dataclass instances with safe defaults, matching Groq's behaviour.
